The five acts

This is the argument for why LangSmith is worth paying for. It's a real sequence that actually happened, which is why it holds up under questioning.

01

The symptom

First baseline experiment scored 16/18. Two cases failed: artist and no-inventory. The obvious read is that the agent is weak on recommendations and on handling an empty catalog.

02

The trace says otherwise

Open the failed run and read the spans. On artist, the agent returned three genuine AC/DC tracks with correct IDs and prices. The catalog stores Let's Get It Up with a straight apostrophe. The model wrote it with a typographic one, U+2019. The evaluator matched track names as a literal substring, counted two instead of three, and reported a failure.

On no-inventory, the agent correctly refused to substitute another artist. The empty result reached the evaluator as the string "[]" rather than a parsed empty list, so the equality test missed it.

Say this: both failures were false negatives. The agent was right and the evaluation was wrong. Without the trace, the rational next move is to tighten the prompt of a working agent — a day burned making the answers worse.
03

Fix the evaluator, not the agent

Unicode normalization with quote folding before the match, and accept both forms of an empty result. Same dataset, same model, rerun: both variants move 16/18 → 18/18.

Then the metric saturates. On the current 22 cases every variant scores 22/22, including four cases added specifically to probe what the candidate prompt claims to fix. The baseline passes all four unaided.

Say this: a test that always passes cannot rank two good versions. And weakening the baseline to open a gap would be lying to yourself.
04

The judge finds what the checks cannot

Add an LLM-as-judge scoring answer usefulness 1–5 against a rubric. It immediately surfaces a defect nothing deterministic was looking for: in 10 of 21 judged cases the agent quotes prices as bare numbers. It was obeying its instruction never to invent a currency — but a customer reading 0.99 has no idea what unit that is. Same category back every time: currency omitted.

05

Feedback becomes the next version, and the gain is measured

One instruction into the candidate prompt: state once per reply that the catalog records amounts without a currency field, never guess one, and close with a next step where one applies. Same dataset, same model, rerun.

Land it here: trace to diagnose, dataset to hold the regression, deterministic checks for what must never break, a judge for the quality those checks can't see, and a measured rerun to prove the change helped instead of assuming it did.

Questions they'll ask

The first one is the question you should expect hardest, because it's the honest weakness in your own headline number.

Your judge is scored by the same model family as the agent. Why should we believe it?

You shouldn't believe it alone, and I don't present it alone. It's paired with deterministic checks that a model can't talk its way past, and with human review in the annotation queue — where a person scored the same ambiguous case 3/5 and agreed with the judge.

The defect it found was independently verifiable: the agent was quoting bare numbers with no currency. Anyone can read the answers and confirm that. The judge found it faster than a human reading 22 transcripts, which is the actual claim. n=21 on one dataset is a demonstration of process, not a reliability guarantee, and I'd want a much larger set before betting a release on it.

Is customer isolation just a prompt?

No. Identity comes from trusted runtime context, never from chat or a model-chosen argument. Every tool revalidates it. Owned-invoice queries filter on customer and invoice ID together, and a missing invoice returns the same response as someone else's — no existence oracle. The thread is bound to a customer and rechecked before model calls and before resumed tool execution.

The honest limit: Studio is a trusted operator environment. A real customer endpoint needs authentication and per-thread authorization before the graph is ever invoked. Middleware protects execution; it doesn't turn a dev API into an authenticated service.

Why one agent instead of a custom graph?

These tasks share one customer context and a four-tool surface. A single tool loop is easy to inspect, easy to trace, and easy to evaluate. A router or multi-agent split would add coordination surface without a demonstrated benefit. If a workflow appeared that needed genuinely different state — a long investigation with planning and delegation — that's where Deep Agents earns its complexity, and I'd reach for it then.

Why not let the model write SQL?

The workflows need a small, known set of queries. Fixed parameterized queries make ownership enforcement and data exposure something you can read and audit in one file. Arbitrary SQL moves the security boundary into the model's output, which is the one place you can't test exhaustively. This also isn't a SQL exercise — the brief says as much.

Can the model approve its own ticket?

Not through chat and not through a tool. HumanInTheLoopMiddleware interrupts the proposed call before execution. A human resumes it. On resume, ownership is rechecked, and the ticket key is derived from the thread and tool-call ID so replaying the same action returns the existing ticket rather than creating a second one.

Does LangSmith make the agent reliable on its own?

No, and I'd be careful of anyone who says it does. It supplies evidence: traces to diagnose behavior, datasets and experiments to test a change, human feedback to widen coverage. Your team still defines what good means, fixes the failures, and watches for regressions. What it removes is guessing — which, as the evaluator bug shows, is where the expensive mistakes come from.

What would you change for production?

Authentication and per-thread authorization derived from server context. A durable checkpointer and database sized for concurrency. Operational monitoring and alerting on the traces you've already got. And a substantially larger, more representative evaluation set — 22 cases demonstrates the process, it doesn't certify the system.

Stay honest here

Each of these is something a sharp listener will notice on their own. Saying it first is strength; being caught is not.

  • Lead with the tie, don't bury it. Deterministic checks sit at 22/22 across all three variants. Frame it correctly: the safety and grounding checks never regressed, and the improvement is in answer quality. If they find it before you say it, it looks like you hoped they wouldn't.
  • The gain is judge-measured, on 21 scored cases, on one model. Call it a demonstration of a process, never proof of production reliability.
  • Support tickets are a labeled local demo extension to Chinook. No refunds, no external system, nothing leaves the machine.
  • Dates in the data are dataset facts, not recent transactions. "Latest" is resolved from the historical records, not from today's calendar.
  • The dataset is generated from code, not edited in the UI. There's an integrity guard that refuses to run an experiment if the cloud dataset has drifted from its definition — because a dataset that silently changes invalidates every comparison built on it.
  • Chinook has no currency field. That's why the agent says the unit is unspecified rather than picking one. It's the defect the judge caught, and now it's a feature you can point at.
