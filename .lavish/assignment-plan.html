Original assignment

Three workflows, one customer story

01 / Discover music

“Recommend three rock tracks I don’t already own.”

Search the real catalog, consult the signed-in customer’s purchase history, return actual tracks and prices with a short explanation.

Value: relevant discovery without invented inventory.

02 / Explain a purchase

“What was in my most recent order, and why did it cost that much?”

Find this customer’s latest invoice and explain its line items and total. Resolve “latest” from the historical dataset, not today’s date.

Value: faster routine support with grounded answers.

03 / Escalate a problem

“I have a problem with that purchase. Open a support request.”

Prepare a ticket linked to an owned invoice, pause for a human reviewer, then persist only the approved request. Rejecting creates nothing.

Value: controlled action. Tickets are a clearly labeled demo extension; no real refunds.

Proposed technical choices

Python + one LangChain create_agent + narrow tools + SQLite + Studio. Let the agent choose tools and handle follow-up questions. Use the existing LangGraph runtime underlying the agent for state and interrupt/resume behavior. Start with four tools: catalog search, own purchase list, own invoice detail, and support-request creation.

Customer isolation belongs in code. Supply a customer identity through trusted runtime context, never from chat or a model-selected customer ID. Every customer query must enforce ownership with parameterized SQL; fail closed when identity is missing. Bind threads to the same customer. Studio’s operator-selected demo identity is a simulation of authentication, not a production login system.

Middleware with visible business value. Human-in-the-loop approval on ticket creation; bounded model/tool calls and clear tool-error handling. Use a unique request key so resume/retry cannot duplicate a ticket. Recheck invoice ownership on execution. Keep Chinook read-only and the small ticket extension separate.

Why this architecture rather than a larger system?

Single agent — recommended: enough for three closely related support tasks, easy to inspect in Studio, fewer moving parts to explain and evaluate.

Custom LangGraph workflow: useful when strict stages and branching dominate. Add only if the chosen support process needs more control than middleware provides.

Deep Agents: explain its planning, filesystem, and delegation capabilities, but do not add those costs to a short support interaction. Its value becomes clearer for long-running, multi-step investigations.

Skip a custom frontend, vector database, arbitrary SQL tool, multi-agent routing, real payment integration, and deployment work.

LangSmith is the centerpiece

  1. Studio: run the customer conversation and inspect the actual agent/tool flow.
  2. Trace: follow a bad recommendation back to the tool output or prompt; inspect inputs, outputs, latency, and token/cost information where supported.
  3. Dataset: turn that observed failure into a regression example; use a small curated set of about 15–20 cases covering recommendations, invoices, privacy, ambiguity, and approvals.
  4. Experiment comparison: run baseline and improved behavior on the same cases with the same model/settings. Use deterministic checks for ownership, catalog validity, totals, and write behavior; use a rubric for answer usefulness.
  5. Human feedback: review an ambiguous result in an annotation queue and show how it feeds another dataset iteration. Confirm workspace feature access early.

Use a genuine observed failure for the improvement story. Keep security controls present in both versions. Report measured results honestly; a small demo dataset is not proof of production reliability.
